# dbt-toolset

Turn the models and metrics of a dbt project into read-only query tools for AI agents,
one tool per model or metric, so access can be granted tool by tool.

It has two halves, joined by one file:

1. **`compile`** (build time) reads a dbt project and writes a *toolset artifact*
   describing the tools.
2. **The runtime** loads that artifact and serves the tools, either as an AWS Lambda
   behind a Bedrock AgentCore Gateway target or as a standalone MCP server. It never
   needs dbt or the dbt project.

Callers never write SQL. They pass structured arguments (columns, filters, group-by),
which are validated against the artifact and run on Amazon Redshift through the
Data API. Everything it depends on is open source.

Deploying it (the Lambda, the Gateway target, IAM) is up to you and out of scope here.

## Compile

```bash
pip install "dbt-toolset[compile]" dbt-redshift
```

```bash
dbt-toolset compile --project-dir path/to/dbt_project --config toolset.yml --out toolset/
```

Compiling parses the project and applies your selection with dbt's own logic. It needs
a valid profile but never connects to the warehouse.

`toolset.yml`:

```yaml
select: "tag:exposed"      # models: any dbt node selection, or `selector: <name>` from selectors.yml
exclude: "tag:pii"         # optional
tool_name_prefix: ""       # optional
limits:
  default_limit: 100       # rows returned when the caller gives no limit
  max_limit: 1000          # hard cap
metrics:                   # optional; needs the `metrics` extra (see Metrics)
  select: "path:models/marts/metrics"
  exclude: "internal_margin"
  tool_name_prefix: ""
```

Nothing is exposed unless selected. Outputs:

| File | Purpose |
| --- | --- |
| `toolset.json` | The artifact the runtime loads. Format: [`schema/toolset-v1.schema.json`](schema/toolset-v1.schema.json). |
| `gateway-tools.json` | Tool definitions (name, description, input schema) to register as the inline tool schema of a Gateway Lambda target. |

### Columns and types

Columns come from `catalog.json` when there is one (`dbt docs generate`; found at
`target/catalog.json` or passed with `--catalog`), otherwise from the columns
documented in the model's YAML, typed by their `data_type`. A model with no known
columns fails the compile. Columns of unrecognised type (for example `super`) can be
returned but not filtered or aggregated.

### Per-model overrides

```yaml
models:
  - name: customers
    config:
      meta:
        dbt_toolset:
          tool_name: query_customers     # default: the model name
          description: Shown to the agent instead of the model description.
    columns:
      - name: internal_note
        meta:
          dbt_toolset:
            hidden: true                 # never exposed
```

## Model tools

Each takes:

| Argument | Meaning |
| --- | --- |
| `columns` | Columns to return (default: all exposed columns). |
| `filters` | List of `{column, op, value}`, combined with AND. Ops: `eq ne gt gte lt lte in not_in between like is_null is_not_null`. |
| `group_by` | Columns to group by. |
| `aggregations` | List of `{function, column, alias}`. Functions: `count count_distinct sum avg min max`. |
| `order_by` | List of `{column, direction}`. |
| `limit` | Capped at the tool's maximum. |

Every tool returns:

```json
{"columns": ["status", "total"], "rows": [["shipped", "25.25"]], "row_count": 1, "truncated": false}
```

`truncated` is true when more rows matched than the limit allowed. Invalid calls come
back as `{"error": "..."}` (an error result over MCP) with a message the agent can act on.

## Metrics

Metrics defined in dbt's semantic layer can be exposed too, one tool per metric. SQL is
generated by [MetricFlow](https://github.com/dbt-labs/metricflow) (Apache 2.0) running
in-process. No dbt Cloud / dbt platform account or Semantic Layer API is involved.

```bash
pip install "dbt-toolset[compile,metrics]" dbt-redshift
```

Each metric tool takes:

| Argument | Meaning |
| --- | --- |
| `group_by` | Dimensions to break the metric down by, e.g. `metric_time`, `customer__region`. Omit for a single total. |
| `time_grain` | Grain for time dimensions in `group_by`: `day week month quarter year`. |
| `filters` | List of `{dimension, op, value}`. Applied before the metric is computed; the dimension need not be in `group_by`. |
| `order_by`, `limit` | As for model tools. |

The dimensions offered are those MetricFlow can reach for that metric, including ones
on joined semantic models. **Granting a metric tool therefore grants those dimensions'
values.** Narrow them per metric:

```yaml
metrics:
  - name: revenue
    config:
      meta:
        dbt_toolset:
          tool_name: revenue_by_period               # optional
          dimensions: [metric_time, customer__region]   # allow-list, or:
          exclude_dimensions: [customer__email]
```

Things to know:

- **Selecting metrics.** dbt (1.12) does not match metrics on `tag:` or `config.`
  selectors. Select them by name, `path:` or `fqn:` instead.
- **The artifact embeds dbt's whole `semantic_manifest.json`** (definitions only, no
  data), because MetricFlow needs it to plan joins. Only selected metrics become tools.
- Each metric is test-compiled at build time, so a metric MetricFlow cannot render
  fails the compile rather than the agent's first call.
- Entities (join keys) are not offered as group-bys.

## Runtime

```bash
pip install "dbt-toolset[runtime]"            # add ,metrics if the artifact has metric tools
```

Configuration is by environment variable:

| Variable | Meaning |
| --- | --- |
| `DBT_TOOLSET_ARTIFACT` | Path to `toolset.json` (default `./toolset.json`). |
| `DBT_TOOLSET_REDSHIFT_DATABASE` | Database to connect to. Required. |
| `DBT_TOOLSET_REDSHIFT_WORKGROUP` | Redshift Serverless workgroup, **or** |
| `DBT_TOOLSET_REDSHIFT_CLUSTER` | provisioned cluster identifier. Exactly one. |
| `DBT_TOOLSET_REDSHIFT_SECRET_ARN` | Secrets Manager secret for database credentials. Optional. |
| `DBT_TOOLSET_REDSHIFT_DB_USER` | Database user for temporary credentials (provisioned). Optional. |
| `DBT_TOOLSET_QUERY_TIMEOUT_SECONDS` | Default 60. The statement is cancelled on timeout. |

With neither a secret nor a user, the Data API uses the caller's IAM identity.
AWS region and credentials come from the usual boto3 sources.

### AWS Lambda behind an AgentCore Gateway

The Gateway is the MCP server; the Lambda is a plain handler:

```
dbt_toolset.runtime.lambda_handler.handler
```

The [`Dockerfile`](Dockerfile) builds a container image with your artifact baked in:

```bash
docker build --build-arg ARTIFACT=toolset/toolset.json --build-arg EXTRAS=runtime,metrics -t my-toolset .
```

Register the function as a Gateway Lambda target, with the contents of
`gateway-tools.json` as its inline tool schema. The Gateway then exposes each tool as
`<target name>___<tool name>`, which is the unit you grant access on.

The function's role needs `redshift-data:ExecuteStatement`, `DescribeStatement`,
`GetStatementResult` and `CancelStatement`, plus whatever your credential method needs
(`redshift-serverless:GetCredentials`, `redshift:GetClusterCredentials` or
`secretsmanager:GetSecretValue`). Give its database user `SELECT` on the exposed
relations only: that is your second line of defence.

Gateway tool schemas accept a reduced set of JSON Schema keywords, so in
`gateway-tools.json` the allowed values are listed in descriptions rather than as
enums. The runtime validates every call regardless, and accepts list values passed as
JSON-encoded strings.

### Standalone MCP server

```bash
pip install "dbt-toolset[mcp]"
```

```bash
dbt-toolset serve --artifact toolset/toolset.json                     # stdio
```

```bash
dbt-toolset serve --artifact toolset/toolset.json --transport http    # http://127.0.0.1:8000/mcp
```

The HTTP transport has no authentication of its own; put it behind something that does.

## How queries are kept safe

- Table and column names come only from the artifact and are always quoted. An
  argument naming anything else is rejected before any SQL is built.
- Values are never placed in SQL text. They are type-checked against the column and
  bound as Data API parameters. This holds for metric filters too.
- Only `SELECT` statements are ever generated, and every query carries a `LIMIT`.
- A tool can only reach its own model's exposed columns, or its own metric and listed
  dimensions. There is no tool that accepts a model name or SQL.

## Other warehouses

Only Redshift is implemented. The seam is the `Executor` protocol in
[`runtime/executor.py`](src/dbt_toolset/runtime/executor.py): `execute(sql, parameters)`
with `:name` placeholders. The test suite's DuckDB executor is a 10-line example.
Generated SQL is Redshift dialect; another warehouse would also need a dialect switch in
`runtime/sql.py` and `metricflow_engine.py`.

## Development

```bash
uv sync
```

```bash
uv run pytest
```

The suite compiles the sample project in `tests/fixtures/sample_project`, checks the
generated Redshift SQL as text, and executes it for real against DuckDB (metrics
included, using MetricFlow's DuckDB renderer). The Redshift Data API client is faked.

`tests/integration/` runs the real Data API path and is skipped unless
`DBT_TOOLSET_TEST_REDSHIFT_*` is set (see the file). Point it at real Redshift, or at
[AWS Emulator](https://github.com/aws/aws-emulator) running locally:

```bash
aws-emulator --telemetry off
```

Then, in another shell, set the variables from the emulator's
[SDK guide](https://docs.aws.amazon.com/emulator/latest/userguide/point-sdk-to-emulator.html)
(`AWS_ENDPOINT_URL`, `AWS_CA_BUNDLE` and so on), create a workgroup once, and run the suite:

```bash
aws redshift-serverless create-namespace --namespace-name dbt-toolset --db-name dev --admin-username admin --admin-user-password 'Passw0rd!x'
```

```bash
aws redshift-serverless create-workgroup --workgroup-name dbt-toolset --namespace-name dbt-toolset
```

```bash
DBT_TOOLSET_TEST_REDSHIFT_DATABASE=dev DBT_TOOLSET_TEST_REDSHIFT_WORKGROUP=dbt-toolset uv run pytest tests/integration
```

The emulator exercises the Data API plumbing (submit, poll, page, typed results, bound
parameters) but its SQL engine is not Redshift. As of 1.0.385 it evaluates
`CAST('2024-02-01' AS DATE)` as the number 2024 and rejects three-part table names, so
one date-filter test is an expected failure there and metric tools are not covered.
Treat a pass on the emulator as a check of the plumbing, not of the SQL.

After changing the artifact models, regenerate the published schema:

```bash
uv run dbt-toolset json-schema > schema/toolset-v1.schema.json
```
